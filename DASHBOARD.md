# Order workspace

The existing authentication and Admin workspace are retained. Active staff and investor profiles with a store assignment mount the modular dashboard from `dashboard.js`; newly onboarded employees reload after store connection.

`dashboard-core.js` contains columns, grouped-order calculations, duplicate-run detection and safe ID-link parsing. `dashboard.css` scopes all layout rules to the order workspace. `supabase/order-dashboard.sql` is the hosted migration source (applied as `order_dashboard`); apply once to a new project.

## Storage and access

Order rows, platform settings and expenses live in the non-exposed `fulfillment_private` schema, with RLS enabled and no client table grants. The authenticated `order_workspace` RPC checks the current active profile and assigned store on every call. Its intentional SECURITY DEFINER boundary is required to read private tables; anonymous execution is revoked. Investors receive an explicit field allowlist and cannot mutate any workspace data. No service key is present in the browser.

Row UUIDs are generated by Postgres and survive edits and full-row moves. `supabase/spreadsheet-grid.sql` upgrades the API to atomic monthly snapshots with a period revision and soft deletion for undo. Stale revisions reject the entire batch. A conflict keeps unsaved data visible; Refresh explicitly offers to discard it. Empty trailing rows are UI-only; blank interior positions are sparse gaps, not saved empty records. Edits queue during saves; period switching and logout await them. Old tabs must reload before editing after this migration.

## Spreadsheet grid

`sheet-model.js` handles TSV, validation and sparse row operations. `sheet-grid.js` owns selection, temporary cell editors, clipboard, history, chip menus, row operations and virtualization. `sheet-grid.css` uses the reference sheet's Arial typography, grid/header colors and dropdown-chip colors. Each month starts at row 1, with 20 blanks after its last populated row. The requested refinement removes the letter row and formula/reference bar; column-name headers retain column selection and resizing. Sidebar starts collapsed. Column widths and per-period row heights persist per user/store in private grid preferences.

`sheet-format.js` supplies the single formatting toolbar, palettes, custom HEX/RGB dialog and border/alignment popovers. `sheet-palette.js` contains the 80 native palette swatches and 8 theme swatches read from the live reference, in displayed order. `sheet-format-model.js` handles default alignment, formatting shifts, shared borders and color conversion. `sheet-format.css` scopes the visual refinement. Selection preserves single-cell fill/text colors; ranges receive the reference's light overlay. Cell editors inherit formatting and all cells are vertically centered. No vertical-alignment control is present.

Apply `supabase/spreadsheet-formatting.sql` after the grid migration. Formatting is shared store/period metadata in private `order_formats`, independent of order values. It commits atomically under the existing period revision, with an allowlist of format fields, sizes, alignments, HEX colors and border styles. Blank-cell formatting does not create order records. Investor reads filter formatting to their existing field allowlist; writes remain denied. Formatting, row edits and clipboard moves participate in the existing 50-step session history; Ctrl+Shift+Z redoes and Ctrl+B/Ctrl+I format the selection. Row clear preserves formatting; row insert/delete shifts it. Old clients that omit formatting preserve existing metadata.

Reference interaction QA was performed on a private copy of the user's native Google Sheet: typing, Tab/Enter origin, double-click editing, range cut/copy/paste, row insert/delete/clear/resize, column selection and resizing, chip selection/clearing and scrolling. The original sheet was not edited.

Practical boundaries: fixed business columns cannot be inserted/deleted; column menus provide clipboard, clear and resize. Calculated/system fields are protected. This is not Google's full formula, formatting or collaboration engine. Browser clipboard permissions can require the keyboard shortcut instead of a context-menu paste. Undo history is session/period local (50 edits); deleted records are retained privately to restore IDs. Annual analytics and Investor access are read-only.

## Calculation rules

- Adjacent rows sharing Order ID or Purchase ID are one calculation group, within a month. The first row displays group gross profit and margin; a green border surrounds multi-row groups. Separate runs of the same ID receive red warnings.
- Unique Order IDs determine order count. Earnings and costs sum across all rows. A group's gross profit requires at least one earning and product-cost value. Blank shipping/additional costs are zero.
- Tax = 15% of positive gross profit minus expenses. Net = gross minus expense minus tax. Average margin is the arithmetic mean of eligible group margins, bounded to -100%..100% as in the reference sheet. Average daily orders uses dates with order activity, rounded to an integer.
- Categories use unique-order total revenue: Small < $12, Medium $12–29.99, Large >= $30. Profit is attributed to the first Order ID in a connected calculation group. Positive category profits determine pie areas; category losses remain separately labelled. Daily bars retain negative values and use recorded dates.
- Year/month controls all calculations. Other filters affect only the table. Yearly Analytics is read-only; select a month to edit. Order date must match its selected month/year.
- Status options are fixed. Platform options are store settings, default Amazon; removing an option preserves existing values.

No Sheet or HTML demo records are imported. Card styling is provisional pending the user's color selection. Updates are immediate after local saves; idle sessions refresh every 15 seconds or with Refresh.
